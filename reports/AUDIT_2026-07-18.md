## Drip diagnosis (task 4) — stall is operational, not a logic bug

**Symptom (from brief):** 165 sent, 18 reached `drip_d1`, 1 reached `d1b`, 0
reached `d2`.

**The queue-advancement logic is correct.** Verified by replicating
`loadDripQueue`'s inner loop (`scripts/drip.js:120-175`) against fixtures:
a lead 20 days out with only `d1` sent advances to `d1b` (both channels); with
`d1+d1b+d1c` sent it advances to `d2`; at 5 days out nothing is due (cadence gate
holds); an email-only lead produces no phantom SMS step. All drip templates exist
for every step/channel (`config/templates.json` → `drip.{d1,d1b,d1c,d2}.{sms,email}`),
so the `if (!tmpl) break` at `scripts/drip.js:159` does not fire. Pitcher writes
the exact fields drip reads — `email_sent_at`/`sms_sent_at` (`scripts/pitcher.js:408,415`
vs `scripts/drip.js:146`) — so there is no field mismatch.

**Root cause: drip is not run on a cadence.** `18 + 1 + 0 = 19` total drip
messages ever sent ≈ one run at `daily_limit: 20` (`config/drip-config.json:9`). A
per-lead advancement bug would show ~165 stuck at `d1`, not 18. Corroborating:
`config/drip-config.json` → `last_run: null`, `today: "2026-06-01"`; `state.json`
contains zero `drip_*` statuses. `scripts/drip.js` is `auto_run:false`, requires
`--force`, and is Mac-only (Twilio + Zoho SMTP). `scripts/setup-cron.js:52-57`
only *prints* a 9am drip cron line for manual `crontab -e` paste — it installs
nothing. The follow-up sequence never ran regularly, so touches 2-6 never
happened for ~147 leads.

**Secondary fragility (real, in code):** `scripts/drip.js:139` silently `continue`s
any lead whose `queue/{id}-brief.json` no longer exists — if briefs are ever
archived/removed, those leads drop out of drip with no log.

**Why no code change was shipped for task 4:** the advancement logic is sound; the
fix is installing/verifying the Mac cron, which cannot be done from the container.
Fabricating a code change to a correct function would be wrong. The remediation is
in CHECKPOINT.md for Dave. (Note: the separate over-send gap — drip not skipping
`reply_drafted`/`unsubscribed`, `scripts/drip.js:135` — is the deferred
campaign-exit work, out of scope this session.)

## Task 6 Phase 0 findings (engagement analyzer) — reported before any code

- **`molly/lib/instagram-insights.js` is real, not stubbed.** Read-only Graph API
  v19.0: `getRecentMedia` + `getMediaInsights` + `getWeeklyInsights` pulling
  impressions/reach/saved/profile_visits/likes/comments and computing
  `engagementRate` (`molly/lib/instagram-insights.js:45-82`). `isConfigured()`
  gates on `INSTAGRAM_ACCESS_TOKEN` + `INSTAGRAM_BUSINESS_ACCOUNT_ID` (line 13-14)
  and skips gracefully when unset. It does **not** cover shares, Reels metrics
  (plays / avg watch time / completion), or LinkedIn.
- **`molly/lib/buffer.js` is real but write-capable** (`schedulePost`,
  `uploadImage`) — not usable as-is for a read-only analyzer.
- **Has insights ever run live?** Almost certainly never for Molly (no cron, token
  unset). Milly/Miley run weekly analytics workflows (success), so their insights
  path has the best chance of having touched live data — but only if tokens are
  set on the Actions side.
- **Sibling boundary: there is none.** Milly and Miley do **not** import from
  `molly/` (`grep require molly/ in milly|miley` → empty). Each sibling has its
  own copy of `buffer.js`, `instagram-insights.js`, `store.js`. Milly's and
  Miley's `instagram-insights.js` are byte-identical (same md5); Molly's differs
  slightly. So the analyzer must be a **new shared module** (`engagement/` at
  root, per the brief) that all three consume — there is no existing shared lib to
  extend.
- **Schema divergence — the join is the hard part.** The three record different
  content-log shapes:
  - Miley: array of flat post objects — `slot, day, time, format, contentType,
    paletteKey, reel_style, product, ctaStyle, hook, body, caption, source,
    evergreenId` (`miley/output/content/content-2026-07-06.json`).
  - Molly: `{ weekOf, generatedAt, researchMode, niches, posts:[{carousel,
    caption1, trevo_found, reel}], glossaryTerms, imagePaths }` — nested, no
    top-level day/time/format/hook (`molly/output/content/content-2026-06-10.json`).
  - Milly: `output/` not populated in-container.
  The analyzer must read each sibling's real fields via a per-brand adapter and
  **must not invent a common schema.**
- **No stored join key.** Neither `store.js` persists the posted Instagram
  `media_id`/permalink back onto the generation record — Miley's marks
  `status:'posted'` + `postedAt` only (`miley/lib/store.js:259-260`); Buffer
  returns its own `updateId`, not the IG media id (`molly/lib/buffer.js:94`). So
  joining live insights (keyed by IG media id) to generation metadata can only be
  done by **caption text + timestamp proximity**, not a stored id. This is the
  central design constraint for task 6 and should be settled before building.

**Recommendation for task 6:** build one `engagement/` module, three named brand
targets (each loading its own sibling's context + account config), read-only,
`--fixtures` path, ≥20-post gate, per-attribute denominators, three never-pooled
reports. Do not modify any sibling's CLAUDE.md/templates/brand files. Not started
this session (large, multi-file; sequenced after this audit).
